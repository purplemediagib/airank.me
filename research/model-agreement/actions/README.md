# Finite GitHub Actions alternative: offline proposal

The disabled YAML is **not a registered workflow**, not pushed, and cannot start paid work. It runs the same Python runner and tests. Paid operation requires explicit reviewed-release environment variable, an exact reviewed head hash, manifest_RELEASE.json, protected environment approval and all existing live manifest gates. None are supplied by this template.

## Why this hosting option
A standard `ubuntu-latest` GitHub-hosted runner in a public repository is intended to remove the research app's ongoing Bunny compute/IP/volume cost. Verify current GitHub plan/runner pricing and repository visibility before activation; do not substitute private, self-hosted or larger runners. GitHub job timeout is 180 minutes, independent of the collection process. There is no server kept alive between jobs. Existing private Bunny archive storage still costs money; retention, size, network and provider charges remain within the same USD40 ceiling. Provider requests already accepted can finish/bill after job cancellation. The API ledger/reservation bounds remain essential and OpenAI's unresolved bound remains a blocker.

## Isolation
Only workflow_dispatch, no push/PR/schedule triggers. Contents read only, no OIDC, no write token, no cache, no artifacts, no public raw data, no dependency installation. Official checkout pinned at v4.2.2 commit `11bd71901bbe5b1630ceea73d27597364c9af683`; sparse checkout excludes other repository code, submodules and LFS; persisted git credentials disabled. An environment variable records the exact independently reviewed commit; dispatched revision and checked-out HEAD must match before Python executes. Run only from the reviewed branch/revision. Protected environment `airank-research-model-agreement-v01` must restrict deploy branches and require a reviewer; check protections actually available/enforced. Runner concurrency uses one global study group, cancel-in-progress false. GitHub concurrency serializes jobs but is not a durable queue; a later pending dispatch can replace another pending dispatch, so do not enqueue all rounds. Existing external study worker must be disabled/absent before singleton verification.

## Implemented restore handoff (review before use)
Each new runner starts with an empty ephemeral directory ending `model-agreement-v01`. It must fetch the private immutable archive pointed at by the existing remote head, verify study marker/protocol/archive hash, safely unpack allowlisted regular files only (reject symlinks, traversal, duplicate entries, oversized archives), verify SQLite integrity and logical raw/ledger fingerprint, and refetch head to ensure unchanged before any provider call. Preserve original manifest/slot/attempt identity, unknown held reservations, budget ledger and every prior raw record. Missing state must halt, never auto-initialize or retry. One explicit initial setup is separate from repeated collection jobs; no automatic reset. Archive downloads stay in runner temp paths and are never artifacts/cache/logs. An interrupted job's last backed-up unresolved reservation remains held; human reconciliation is required.

## Qualification and three rounds
1. One explicit initialization of the new private namespace and reviewed manifest, no paid calls. The original Finland study stays untouched.
2. Restore on a fresh job; run one approved diagnostic ID through existing `execute` and snapshot. Repeat only the approved finite diagnostic set, reconciling charges each time. No ad-hoc prompt/model changes. Fail closed if response cost or bound is unavailable.
3. Review diagnostics, then explicitly activate primary manifest using the existing protocol-preserving activation path. Same ledger, no reset. All provider/location/protocol bounds still apply.
4. Dispatch each of the three predeclared rounds separately around its frozen start time. Same 20 prompts ×3 routes/round, counterbalanced order and private result metadata. Read results with existing runner; do not insert new collection methodology or change endpoints. No automatic backfill for a queued/missed window.
5. `job_driver.py` now provides a single-round driver: the existing `service.py scheduled` loop can wait for later rounds, so do not use it unchanged as a one-round driver. Driver calls existing `tick` with selected_round filtering, stops after the selected round ends/completes, and never selects another round. Confirm a reviewed bound for backup+provider time fits inside the job budget. For a 180-minute timeout, execution admits only a complete frozen round window within its 150-minute deadline, reserving time for restore/finalization; do not silently shorten a scientific window to make it fit. If planned window cannot safely fit, request timing change/another justified timeout before dispatch. Runtime expiry and full per-request timeout must fit the selected window; timeout cannot prove every collection will complete.
6. At end, private verified snapshot is authoritative. Cost/reporting reads use that same cohort, distinguish estimates from billed costs and retain failures. Public Actions logs may contain only sanitized state/counts, never raw provider response, prompts, customer data or API exceptions.

## Implemented offline verification
`recovery.py` checks the independently reviewed remote head hash, marker/protocol, archive digest and name, SQLite integrity, restored evidence fingerprint and head stability; rejects existing target, traversal, symlinks, unknown paths and expanded-size overflow. It never initializes a fresh ledger. `job_driver.py` restores then verifies frozen inputs before one diagnostic or one selected round. It passes a finite dispatch deadline checked again after reservation backup. A timeout after reservation retains the private hold; do not rerun with a new ID. Expected-head variable must be refreshed from verified private state and reviewed between jobs, not bypassed with latest automatically.

The workflow uses a 180-minute job hard timeout and 150-minute execution deadline. If checkout/validation is delayed, the outer job can terminate earlier: durable reservation handling remains safe, but completion is not guaranteed. Full planned round must fit the inner deadline; there is no silent window shortening. No automatic init/activation workflow is provided; perform these explicit reviewed operations separately with the same namespace and ledger. All three test files now run 55 mocked tests. No remote calls or paid qualification have been made.
