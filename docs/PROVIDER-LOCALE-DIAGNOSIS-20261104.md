## Confirmed correction

Google AI Overviews monitoring for `GI/en` was rejected before the paid SERP
request because `selectSerpContext` accepted only `location_type: Country`.
DataForSEO's [official public Google SERP catalog](https://cdn.dataforseo.com/v3/locations/locations_serp_google_2026_09_01.csv),
linked by its [location documentation](https://docs.dataforseo.com/v3/serp-se-locations/),
lists Gibraltar as code `2292`, country ISO `GI`, type `Region`, with no parent.
The observed live tasks use GI/en. The original selector rejects this exact row
in an offline reproduction.

The shared `common/dataforseo-location.mjs` selector now accepts that exact
verified root, only when the called endpoint's own catalog actually contains it.
Existing unique Country roots remain accepted. Arbitrary Region/City rows,
wrong codes/names/parents, absent markets and ambiguous roots are rejected.
There is no country substitution, inferred support, paid retry or evidence
rewrite. Both SERP and consumer collectors use the selector, but this SERP
fixture does not establish consumer collector availability.

### Brand extraction configuration disagreement

The UI message comes from `intelligence.enabled`, derived from the
`ENTITY_ANALYSIS_ENABLED` flag in the API/projector's configuration. It does not
independently prove the monitoring worker's flag or readiness. The API refuses
manual analysis when that flag is off. The worker's separate timer and engine
also require the flag.

Existing worker application logs observed on 2026-11-04 at 12:52:23 and 12:53:23
in the dashboard's CET display contain `Entity analysis unavailable; check
migration and worker configuration`. At the exact deployed commit, this warning
is emitted only inside the timer guarded by `ENTITY_ANALYSIS_ENABLED === 'true'`.
It establishes that the emitting worker process was enabled despite the
displayed API/projector state. No environment values were read. This is an
enabled worker with an unresolved execution error and a disagreeing displayed
configuration, not simply globally disabled analysis.

`entityTick` can reject during DB connection/query setup, migration checksum
validation, or engine SQL/transaction work; the catch discards the reason.
A missing OpenAI key or exhausted count cap normally records `MISSING_CREDENTIAL`
or `BUDGET_WAIT` on the job, rather than emitting this generic warning. Nearby
website-autofill and sentiment warnings make shared database latency or
availability plausible, but do not establish causation. Do not flip an enable
flag or rerun a migration merely from this message. Check existing safe logs,
non-secret configuration parity and migration readiness before a remedy.

Enabling the worker is consequential: `intelligence/engine.mjs` automatically
enqueues successful evidence from the first-enable timestamp and can execute
already queued jobs. The default is 25 calls in a rolling day, bounded by
`ENTITY_ANALYSIS_MAX_DAILY_CALLS`, not by the analytics service's monthly hosting
budget. It calls OpenAI with up to 6000 completion tokens. The UI's statement
that analysis is never started automatically is inconsistent with this enabled
worker behavior. Do not enable it as a routine analytics repair.

Relevant configuration names for a later authorized check are
`ENTITY_ANALYSIS_ENABLED`, `ENTITY_ANALYSIS_MODEL`,
`ENTITY_ANALYSIS_MAX_DAILY_CALLS`, and presence only of `OPENAI_API_KEY`.
The API and analytics projector must also agree on output-affecting settings
because the summary format hash includes the entity enabled flag and model.
Clarify manual-only versus automatic extraction and its spend limit before
activation. This patch changes neither mode nor settings.
